# 0004：MCP 短调用任务与文件交付

日期：2026-10-15。范围：个人 Grok Bot 使用现有图片工作台能力。

## 原因

[首轮实测](../logs/2026-10-15-mcp-probe.md)证明原生 MCP 可传入聊天图片并交付 ImageContent，但 120 秒工具调用在约 60 秒超时，当前原生调用面未找到 resources/read。仅增加进度或用 curl 成功替代原生验收都不能解决该限制。

## 选择

- 保留 Go 单实例及官方 MCP SDK，将五个业务操作作为短调用提交，再用普通工具查询状态和领取结果。当前客户端只可靠暴露 tools，所用 SDK 的 Tasks 扩展也不构成已验证链路，因此不手写新的 MCP 协议扩展。
- 有界进程内任务表管理状态、请求去重和临时文件，复用 Go context 与现有 HTTP 上游。个人工作量不需要 Redis、数据库或外部队列；重启失效是明确的使用边界。相同 requestId 与参数复用原任务，避免连接器重试造成重复付费调用。
- 网页与 MCP 共用业务实例与图像处理槽位。小红书只抽取共同的解析、完整文件生成操作，HTTP 仍保留原契约，不通过伪造网页登录或回调本机 HTTP 绕过授权。
- 小文件保留 MCP 标准内容类型用于预览或内嵌文件，并提供文本元数据；所有文件均有单文件、短期有效的下载链接，保证原字节交付。实际 Grok Bot 会重编码部分 JPEG ImageContent，且可能忽略 structuredContent，因此图片通过下载链接交付，超过内嵌阈值时只返回元数据及链接。服务凭据不出现在结果链接中。使用现有磁盘与 Go 标准库完成基础 I/O，不引入通用对象存储抽象。
- Skill 负责选择操作、关联任务和最终交付；参数格式由工具 Schema 和业务实现维护。用户仍通过图片/分享链接表达需求，不管理编码、轮询或请求去重细节。

参数和生命周期集中维护在 [MCP 说明](../../apps/server/MCP.md)，验证事实见[实施记录](../logs/2026-10-15-mcp-business.md)。此决策不扩展到多用户或跨实例持久任务。
